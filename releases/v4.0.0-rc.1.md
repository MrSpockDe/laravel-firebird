# mrspockde/laravel-firebird v4.0.0-rc.1 — preparation

**Status: draft for an unpublished release candidate.** RC1 has not been tagged or
published, and its Packagist availability and fresh consumer installation have not
been validated. `v4.0.0-beta.1` remains the published version. A release candidate
is not a stable release or a production-readiness guarantee.

## Purpose and changes since beta.1

RC1 is intended to consolidate the existing 4.0 implementation, integration
evidence and support boundaries for consumer evaluation. No new driver feature is
introduced by this documentation preparation.

Since beta.1, package discoverability metadata and database-creation guidance have
been clarified. Integration coverage now explicitly verifies the complete
`dropConstrainedForeignId()` lifecycle and the five final audit gaps:

- `mediumText()` / `longText()`: text-BLOB metadata, UTF8/NULL and safe column drop.
- `decimal()`: explicit precision/scale and positive/negative round-trips.
- `date()` / `time()`: native metadata, values/NULL and column lifecycle.
- `ipAddress()` / `macAddress()`: VARCHAR(45)/(17) storage, values/NULL and lifecycle.
- `timestampsTz()` / `dropTimestampsTz()`: native TZ columns, removal preserving
  other columns/data and successful subsequent inserts.

The current support reference replaces outdated descriptions of already existing
view introspection, schema wipes, comments, virtual computed columns, modern
identifiers and identity options. These are not all new features since beta.1.
The FK-drop architecture review found no functional defect; execution-time
metadata resolution remains in place. Direct `toSql()` consumers must account
for the internal `ForeignKeyDrop` operation rather than assume only SQL strings.

## Migration and schema scope

The [current support reference](../docs/migration-support.md) details integration
evidence for identity/generated IDs; table and column create/drop/alter lifecycles;
primary/unique/regular indexes; foreign keys and tested actions; column/index/FK/view
introspection; comments; virtual computed columns; native BOOLEAN/TZ types; and
Laravel convenience helpers. The [roadmap](../docs/roadmap.md) separates achieved
scope from post-4.0 candidates. No complete Laravel API parity is claimed.

Important boundaries remain:

- Signed integer mappings, without unsigned range enforcement.
- JSON/JSONB text storage, not native JSON semantics; ENUM is tested VARCHAR+CHECK.
- TZ tests cover representative offsets/fractions, not all named-zone/DST cases.
- Blueprint temporary tables, table/index rename, spatial indexes,
  `useCurrentOnUpdate()`, stored/persisted computed columns and computed CHANGE
  are unsupported, as are `year()`, `geometry()` and `vector()` mappings.
- Explicit charset/collation CHANGE and enum CHANGE are rejected. CREATE/ADD
  charset/collation and `virtualAs()` are supported in the tested scope.
- DELETE/UPDATE CASCADE, SET NULL and NO ACTION are tested; explicit RESTRICT is
  rejected. SET DEFAULT has no integration-tested behavior guarantee.
- No automatic migration transaction guarantee; wipe-specific failure safety
  does not extend to arbitrary DDL sequences.
- Some raw expressions require caller-supplied CASTs. Empty BLOB fetches may be
  `''` or `null` across PHP/PDO clients; the test permits both.

## Database configuration and long-lived application schemas

Unchanged Laravel 13 standard migrations were validated with the published beta,
Firebird 5.0.4, **16384-byte pages** and **UTF8** charset/collation. An 8192-byte
reproduction hit Firebird's index-size limit for the original composite
`failed_jobs` index. This is a schema/platform constraint, not a demonstrated
driver SQL defect or a universal minimum page-size rule. See the
[README setup guidance](../readme.md#database-creation-for-stock-laravel-13-migrations).

For Unix-second columns with a horizon beyond January 2038, applications can
choose BIGINT while preserving nullability. The
[seven-column Laravel 13 / OweFlow recommendation](../docs/migration-support.md#unix-timestamps-and-the-2038-horizon)
is an application-schema choice, not a general driver mapping change or evidence
that unchanged standard migrations fail.
